# Wallet / question checkout rollout

## Active scope and policy
MCQ 20 paisa, SHORT/SQ 30 paisa, CQ 50 paisa. Integer paisa only (৳20 = 2000). First successful login after rollout initializes a non-ADMIN wallet once with ৳20 trial credit. Existing sessions initialize lazily on wallet/quote access. One bonus per database user, not per Google account alias/device/IP; multiple-account abuse prevention and verified-phone controls are not implemented. Trial credit is non-withdrawable, not a cash payout.

Bangla/general MCQ/SQ/CQ builder: server recalculates type/rate from visible persisted questions, deduplicates IDs, shows payable total/balance and asks confirmation. Checkout purchases per-question reuse rights. Already purchased same IDs are free to reuse; ADMIN (fresh DB role) and active APPROVED unexpired packages pay zero. This uses existing time-based packages (no new package quotas). Package expiry after free use does not grant permanent ownership; later wallet checkout may apply. Current prices are code-configured in lib/wallet.ts, not an admin pricing editor.

Wallet debit is for deliberate question checkout, not generation or successful PDF completion. Failed provider generation is never charged by this feature. Canceling the native print dialog does not refund checkout; entitlements remain. No automatic cash refund, withdrawal, transfers or reversal UI. Manual recharge approval uses configured existing payment-info numbers, not an automatic payment gateway.

General builder's app Print/PDF/booklet checks paid entitlement; server saved-paper creation checks again. Paid students can save/list/delete their own papers under existing owner scoping; ownerless legacy remains ADMIN-only. Preview/question-bank API content is still readable as before: browser Ctrl+P/screenshots/copy cannot be securely prevented, and this is not DRM. English writing/grammar practice, quiz/live tests, standalone resources/book purchases, generation quotas and provider balances are not billed by MCQ/SQ/CQ rates. Existing generation quota/locks are unchanged. No redesign of prior screenshot UI in this task.

## Persistence and concurrency
Existing PostgreSQL Setting table: wallet:account:<user>, one wallet:bonus:<user>, one wallet:question:<user>:<id> receipt per purchase, wallet:recharge:<user>:<trx> request with review audit, globally unique wallet:trx:<TRX>. All wallet writes/quotes/bonus, package payment reference reservation and recharge review use one transaction-scoped PostgreSQL advisory lock. Atomic balance + receipts; rejected/stale/insufficient requests roll back. Global serialization is intentionally simple but can become a throughput bottleneck. No schema migration, no personal/payment secrets added to Git.

Recharge: whole taka, minimum20, maximum50000 per request. One pending request/account. No balance increase until ADMIN checks the actual provider statement and approves. Admin role checked from database, no client-supplied owner, amount or status accepted for approval. Same TrxID cannot be reused across accounts/wallet/new package requests; historical package IDs checked case-insensitively. Rejected TrxIDs remain reserved: contact support for correction rather than reuse. Concurrent/repeated approval cannot credit twice. No SMS/provider webhook or automated proof validation. /admin/wallet shows up to200 pending requests. /wallet shows up to50 receipts/recharge records (key-ordered, not a paginated complete chronological ledger). Preserve these Setting records in backups; do not delete financially prefixed keys through generic admin tools.
